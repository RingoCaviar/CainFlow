# Import Agent references through ordinary image nodes

Local issue: `prompt-agent#026`.

Pasted, dropped and uploaded files, and selected or dropped history images, create ordinary ImageImport nodes before becoming usable pending Agent references. Existing scene imports are referenced directly. Each batch reserves attachment positions immediately and serializes imports so asynchronous reads cannot reorder nodes or reference numbers. Agent consumes its own drop and paste events, preserving mixed clipboard text and preventing duplicate global imports.

A reference source adapter owns history metadata, original reads and import/reuse decisions. History browsing loads metadata with local thumbnail URLs; originals are read only for selection or explicit preview. The picker separates scene and history tabs, searches names and history prompts, renders 60 candidates at a time, and separates preview from selection. Previews use the shared fullscreen API without creating nodes.

An imported history node stores `agentReferenceSource: { historyId, assetKey }`. Reuse requires the same history identity, upload mode and unchanged canonical asset. The marker round-trips through node serialization and restoration; the ordinary ImageImport owner protects the image asset. File and history imports use the existing node creation, image persistence and undo lifecycle. Retrying a failed import retains its node identity instead of creating another node.

Removing a pending reference retains any already-created canvas node. Every asynchronous selection is fenced by the original workflow/conversation revision and pending selection identity; cancelled reads cannot create nodes or restore references. Clearing or changing workflows starts a fresh queue. Already-sent references retain the existing self-contained conversation image format, so this change does not migrate old conversation attachments or depend on the source node remaining present. Importing references does not automatically connect them to generation nodes.

For `prompt-agent#029`, applying or generating a Prompt Plan synchronizes its explicit reference list to the target's ordered `referenceImages` input before the execution snapshot. The list replaces old image-input connections, preserves other ports, deduplicates source ports and reuses connection IDs on retry. Legacy plans without a reference list retain existing inputs. Graph changes use the canvas history, connection projection and persistence lifecycle. All sources are validated before graph/prompt writes; missing, disabled, running or changed sources reject application instead of silently producing a text-only request. An image that cannot be individually output by its original node must be imported separately and reselected. Historical message previews remain available independently of source-node existence; that does not authorize substituting a different source when applying an old plan.

For `prompt-agent#030`, an explicit canvas node deletion now removes corresponding Agent references from pending attachments, message/archive attachments and Prompt Plans, and persists that change. This supersedes retaining references after an explicit user deletion; merely restoring a legacy conversation with an absent source does not perform implicit cleanup. The node lifecycle emits actual removed IDs even for nodes without connections, after its undo snapshot and before saving. Agent-side removal remains one-way: it never deletes canvas nodes. Import operations expose source identity before saving, and active reply operations track deletions so late completion cannot resurrect references. Generation result runs remain intact, and reference-strip updates do not replace running result views.

For `prompt-agent#031`, generated-result thumbnails share a single-use in-memory drag token with the Agent and canvas drop handlers. The drag retains the already loaded original image, not a thumbnail or remote URL; only the token enters DataTransfer. Dropping on Agent consumes the event and uses the reference import adapter. Dropping on canvas creates a new ImageImport at the drop position through the existing lifecycle. Result previews remain independent, and workflow changes, source-view disposal or drag completion invalidate unconsumed tokens. Restored and current result batches use the same renderer.
