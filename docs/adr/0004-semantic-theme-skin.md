# Let themes provide semantics and features own component skins

CainFlow themes will provide semantic visual roles, while each feature owns the selectors and state styling for its UI. A theme must not need to understand a feature's DOM structure merely to supply its palette. This seam gives feature styling one authoritative location and lets a theme express visual intent through stable meanings such as surfaces, text, borders, accents, focus, danger, and interaction states.

Feature-specific theme exceptions are disallowed by default. An exception is acceptable only when a distinctive theme effect cannot be expressed through the shared semantic roles; it must remain localized, explain why the shared skin is insufficient, and have targeted visual coverage. The semantic role catalog may evolve as component families are migrated, so this decision deliberately does not freeze a permanent token list.

Migration follows an expand-contract sequence per component family. CainFlow first adds semantic roles and a shared feature skin, verifies every supported theme at the rendered behavior seam, and then removes the corresponding legacy theme-qualified selectors and temporary fallbacks. The settings panel is the first migration pilot; later component families reuse the same architectural seam rather than creating parallel theme interfaces.

Ticket #57 completed the settings main-panel contract phase. Theme files may define only reusable semantic palette values; they may not target `#settings-modal`, `#general-settings`, or main-panel component classes owned by `settings-theme-skin.css`. That feature skin is the sole owner of main-panel structure and component states, including cards, inputs, selects, checkboxes, range controls, buttons, toggles, badges, retry controls, and update status. A source-level guard rejects any future theme-qualified main-panel DOM rule instead of preserving a hash baseline. Auxiliary provider-model and settings-help dialogs remain outside this pilot; they enter the next “common menus and dialogs” component family and do not weaken the main-panel authority boundary.

The next component families must migrate in the order recorded in `docs/semantic-theme-migration.md`. Each family repeats the same expand-contract gates before the following family begins.

Ticket #59 started the expand phase for common menus and dialogs. `menu-dialog-theme-skin.css` maps menu and dialog roles onto the shared panel palette and owns the later cascade for representative context-menu, theme-menu, modal, help, provider-model, and settings-help dialog states. Ticket #60 completed the menu contract: theme-qualified context/theme menu rules are forbidden and the shared theme-menu file retains layout only. Dialog rules remain temporarily frozen behind a source hash guard until the following dialog contract ticket removes them. This component family does not include history/cache content, camera/tools, or nodes/canvas.
