# 测试分层与执行

## 日常修改

小改动以受影响行为为范围，只运行相关测试。共享文件里的局部修改也按实际影响选择。提交前用下面的步骤核对范围。

1. 用 `-DryRun` 检查改动对应的测试文件。静态引用无法识别的间接影响，用 `-Group` 追加对应模块。
2. 对照实际变更核对断言。缺少覆盖时，在同一变更中补写用例或扩充现有用例。新测试登记到 `scripts/test-groups.json`，必要时补充源码关联或影响规则，再预览确认能选中它。
3. 运行选中的测试。纯文档改动和空工作区做基础检查。改动影响程序行为且没有相关测试时，先补覆盖再将检查视为完成。

以下示例从仓库根目录运行。PowerShell 入口也支持从其他目录启动。

```powershell
# 预览选择原因、范围、测试文件和将执行的命令，不运行测试
./scripts/check-daily.ps1 -DryRun

# 检查当前已暂存、未暂存和未跟踪的改动
./scripts/check-daily.ps1

# 已有提交的功能分支：检查与基线的差异，并包含当前工作区改动
./scripts/check-daily.ps1 -Base main

# 人工判断还影响其他模块时追加覆盖，不能缩减自动选择的范围
./scripts/check-daily.ps1 -Group update,desktop
```

验证已经提交的工作时，提供不同于当前提交的 `-Base`。基线必须在本地存在，无效基线会报错。

工作区包含其他未完成修改时，可以用 `-ChangedPath` 显式列出本次任务的**全部**新增、修改和删除路径。此参数替代 Git 检测，输出会标记为显式范围。它与 `-Base` 互斥。发布验证仍检查完整工作树。

```powershell
./scripts/check-daily.ps1 -ChangedPath js/features/update/update-manager.js,tests/update-restart-browser.test.mjs -DryRun
```

跨平台或需要逐项传递参数时使用同一 Node 入口：

```text
node scripts/run-tests.mjs --mode daily --base main --group update --dry-run
node scripts/run-tests.mjs --mode full
node scripts/run-tests.mjs --mode full --group media --dry-run

# 同时保留机器可读的范围、阶段耗时、原始退出码和未执行阶段
node scripts/run-tests.mjs --mode full --report .scratch/full-regression/results.json
```

## 分层与选择规则

`scripts/test-groups.json` 是测试清单和影响规则的来源。每个测试文件有执行层级和模块组。直接修改的测试进入计划。对于源码改动，选择器使用测试及其助手和 fixture 中的静态引用、清单登记的 `sources`，以及影响规则明确列出的测试文件。`--group` / `-Group` 可追加已确认受影响的模块。

拼接路径、运行期调用和语义上的间接影响需要人工核对。预览会列出缺少关联测试的路径和可参考的模块组。实际运行时，缺少关联会使检查失败。手动追加模块后，仍需把已有或新增测试关联到相应改动。

| 层级 | 执行内容 | 日常选择 |
| --- | --- | --- |
| 基础检查 | Git 差异空白检查、改动文件的语法检查 | 按当前改动执行 |
| fast | 低成本逻辑与契约测试 | 相关测试 |
| integration | 服务、进程或数据集集成测试 | 相关测试 |
| browser | 浏览器交互、主题和完整应用链路 | 相关测试 |
| python | 后端行为测试 | 相关测试 |

分组按行为影响维护。修改测试助手、fixture、清单或运行器时，验证受影响的测试和工具行为。执行前核对清单与磁盘，未登记的新测试、缺失的旧测试、非法层级或模块均报错。

默认 fast 并发 4，integration/browser 并发 2，各层顺序执行，避免快速测试与浏览器争抢资源。使用 `-FastConcurrency` / `-BrowserConcurrency`（Node 对应 `--fast-concurrency` / `--browser-concurrency`）调节。先测量耗时与失败率再提高并发。`-Python` / `--python` 同时用于 Python 测试与浏览器助手的后端进程。

每阶段记录通过/失败与耗时；某阶段失败仍执行后续阶段，最终退出码非零。不会自动重跑失败用例或将重跑成功替换首次失败。

浏览器层使用持续补位的 Node 测试队列。每个选中的文件在独立进程中执行一次。快速层每 100 个文件一批，各层之间顺序执行。

浏览器文件清单通过标准输入传递，不受 Windows 命令行长度影响。使用 `--report` 时，每个文件启动和完成都会更新报告的 `fileProgress.browser`，包含正在运行、已完成和未启动的文件，以及原始退出码、信号和耗时。主进程被中断时保留已完成文件的记录；只有整个入口结束后的主报告才表示完整回归结果。

浏览器耗时缓存保存在 `.scratch/test-runner/browser-durations.json`，后续优先启动已知慢文件，减少收尾空等。缓存只影响顺序，不复用通过结果或改变测试范围；缺失或损坏时按清单顺序运行；缓存不可写会提示警告，测试照常执行。失败文件不会用提前退出的耗时覆盖之前成功运行的耗时。

## 全量回归与发布

发布前对最终版本显式运行全量回归。日常工作遇到广泛影响且无法用定向测试覆盖时，说明理由后使用全量入口。日常入口始终保持定向范围，影响不清楚时先核对依赖和测试关联。

```powershell
./scripts/check-full.ps1 -DryRun
./scripts/check-full.ps1

# 发布：全量测试之外，继续验证版本/更新说明、回归工作流及 Media asset 安全
./scripts/validate-release-readiness.ps1 -TagName vX.Y.Z -NoPause
```

`run-local-regression.ps1` 用于发布级回归和源码冒烟。发布检查复用 `check-full.ps1`，清单中的 Python 回归执行一次，覆盖桌面和存储行为。

脚本菜单保留原选项，新增 **8：日常检查**、**9：全量回归**。菜单日常项检查当前工作区；验证已提交分支时用上述带 `-Base` 的命令。

全量通过后再有改动，按新增影响补测。发布时验证最终提交。交付记录注明命令、基线或显式范围、有效层级、失败与复测结果。

### 全量回归收录标准

- 全量回归覆盖常用工作流、关键跨模块契约，以及数据丢失、安全、迁移和恢复等后果严重的回归。每个用例应能说清楚它防止哪类可观察的回归。
- 同一种行为保留能发现回归且成本最低的验证。定期用耗时报告找出重复验证、无效断言和过宽的浏览器矩阵，合并等价覆盖，并保留关键路径的代表用例。
- 特定供应商、少见界面组合或特定环境的专项覆盖继续登记。确认全量已保留代表用例后，可将专项文件标为 `"full": false` 并填写 `reason`。修改相关功能时仍会选中它，也可用 `--group` 追加。发布涉及专项场景时，运行对应专项覆盖。
- 调整收录范围时保留原始失败记录。修复失败或不稳定用例应独立进行，收录判断依据覆盖价值和可替代性。

## 既有数据与不稳定测试

测试使用隔离数据，保留用户模板和配置。回归按清单选出的范围执行，保留真实失败结果。可选 JSON 报告每阶段保存进度，不包含环境变量或请求数据。主进程中断后保留最近检查点及执行中、未执行阶段。首次失败与复测用不同报告路径，便于保留两次结果。

浏览器失败后可单独复测以诊断资源或时序问题，但原始失败必须保留并报告。后续应独立处理不稳定用例与用户数据隔离，不能通过删测试或静默重试提高通过率。

定向浏览器复测与全量串行执行，避免叠加 Chromium 与本地连接资源占用。遇到 `ERR_NO_BUFFER_SPACE` 等系统资源错误时保留原始记录、检查资源占用，不添加请求重试或忽略。持久化状态的轮询可降低读取频率，但保留原来的截止时间和完成条件。

Windows 隔离测试浏览器统一使用 `--disable-features=TcpPortRandomizationWin`，沿用 [Playwright上游兼容修复](https://github.com/microsoft/playwright/pull/43605)。该特性在回环连接中可能产生端口仍可用但报WSAENOBUFS的情况；参数仅作用于测试创建的Chrome进程，其他平台、产品浏览器与系统配置不变，不重试或忽略任何请求失败。

资源受限机器可用 `node scripts/run-tests.mjs --mode full --browser-concurrency 1 --report .scratch/full-regression/serial.json` 降低浏览器并发，覆盖范围不变；交付记录注明实际并发参数，不将默认并发的失败覆盖成成功。

浏览器助手的 `app.step(label, task, { failOnRequests, failure })` 为关键操作标注边界：只将本步骤启动、且匹配指定本地接口的 HTTP/网络失败视作前置失败；`failure` 可检测方案保存失败或批次部分失败等终态。已有负向用例不会因全局收集错误而自动失败。诊断包含请求方法、去掉查询参数的地址、HTTP 状态、请求标识与时间，以及经过清洗的本地 API 错误字段；不记录提交内容、请求头或图片字节。

工作流版本冲突 409 有既有的应用恢复流程，因此 Agent 生成步骤保留这些 HTTP 记录，但依据方案最终状态判定保存是否失败；不能把中间冲突直接视为失败，也不在测试中新增自动重试。

公共浏览器助手的保存等待通过只读状态确认：会话缓存定时器、工作流自动保存队列以及 `diskStorage.waitForKey` 对应的实际写入版本。已经干净的会话不再固定睡眠3.1秒；有修改时仍等待产品真实的自动保存周期，不主动刷新或重试保存。验证自动保存延迟的用例保留原有时序断言。

需要分析整套耗时时，可设置 `CAINFLOW_TEST_METRICS_DIR` 为一个输出目录，再照常运行全量。公共完整应用助手会逐文件记录浏览器启动次数、服务启动/浏览器就绪/清理耗时，以及保存等待次数和总耗时；这些诊断不包含工作流内容或凭据。浏览器文件完整耗时仍以主报告 `fileProgress.browser.results` 为准，诊断计时不替代通过/失败结果。

`uploadImageOriginal` 通过真实文件输入上传，等待本步骤的成功写入响应，再比较存档资源与输入原图的 SHA-256。替换图片不能仅以“已有一张资源”为完成条件。该等待仍为 7.5 秒，存档轮询间隔 200 毫秒；没有增加超时或失败重试。生成链路的前置保存错误应直接报告，不再等待一个已不可能出现的成功 UI。
