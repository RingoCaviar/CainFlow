# 发布版本

## 固定版本号规则：逢十进一

版本格式固定为 `v主版本.次版本.修订号`。每次发布修订号加 1；修订号达到 10 时归零并将次版本加 1；次版本达到 10 时归零并将主版本加 1。次版本、修订号只能为 `0` 至 `9`，主版本不限制位数，各段不得有多余前导零。不得改用 `v3.6.11` 等连续累加修订号的方式。

- `v3.7.8` → `v3.7.9` → `v3.8.0`。
- `v3.9.9` → `v4.0.0`；`v9.9.9` → `v10.0.0`。
- 已发布的历史标签不改名。当前 `v3.6.10` 是历史例外，**下一版固定为 `v3.7.0`**，此后按上述规则递增。

发布说明验证会调用 `scripts/validate-release-version.ps1` 强制检查；仅兼容已发布的 `v3.5.10`、`v3.5.11`、`v3.5.12` 和 `v3.6.10`，不得新增例外。更新仓库规则不会自动修改当前已发布版本号或触发发布。

每次创建或更新 GitHub Release，先在仓库中提交 `docs/releases/<tag>.md`。例如 `v3.5.7` 使用 `docs/releases/v3.5.7.md`。说明文件与版本号修改一起进入发布标签所指的提交；发布工作流直接读取该文件作为 Release 正文。

## 更新说明格式

参照 [v3.5.6](releases/v3.5.6.md) 编写，按以下顺序填写：

1. `## 🚀 <版本号> 更新内容`：用主题小节和具体条目说明用户能观察到的新增、修复或行为变化。
2. `## 💡 升级说明`：写明是否需要迁移、备份或额外操作；无需操作时明确说明。
3. `## 📦 下载`：列出本次实际发布的包名与平台。
4. `## 🔗 完整变更`：链接到上一正式版本与本版之间的 GitHub compare 页面。

内容应对应本次标签包含的实际改动。发布前运行 `scripts/validate-release-notes.ps1 -TagName <tag>`，确认文件和结构有效。占位内容不能用于发布。

## 发布步骤

1. 完成代码复核与发布门禁，更新 `js/core/constants.js` 中的版本号，并编写对应版本说明。
2. 按 `AGENTS.md` 的要求提交中文提交信息及本地 Issue ID，然后推送提交与版本标签。手动触发发布工作流时，也要填写已有对应说明文件的标签名。
3. 等待 `.github/workflows/release.yml` 成功，检查 GitHub Release 的正文、目标提交、平台包和下载文件名。发布后的文字修正应同步修改说明文件及 GitHub Release。
